> 类型：架构扩展规划（前端单体 → 前端 + 后台服务）· 版本 v1.0（2026-07-24）
> 现状基线：前端 v0.11.0-alpha.1（commit 440d9f5）· 配套《需求规格说明书 v1.1》《需求规划文档 v1.0》《Gap 分析与演进规划 v1.0》

## 1. 为什么需要后台（从角色痛点反推）

不是"因为可以加"，而是四类角色各有一件事在纯前端里**结构性做不到**：

| 角色 | 纯前端做不到的事 | 根因 | 后台解法 |
|---|---|---|---|
| 算法研究者 | 跨会话积累与对比运行结果 | 刷新即失，KPI 只活在内存 | 运行归档 API（PR-BE-2） |
| 算法研究者 | 扫参：几十组配置跑完排名 | 浏览器单线程，跑一组要占用界面 | 服务端并发扫参（PR-BE-4） |
| 集成开发者 | 接真实电梯遥测 | 浏览器无法监听 MQTT/设备回调 | 遥测桥 WebSocket（PR-BE-6） |
| 展厅演示者 | 把一次漂亮的运行留给同事复现 | URL 只能带配置，带不了结果 | 场景/结果分享短链（PR-BE-5） |

**判据**：以上四条都不是"体验更好"，而是"纯前端架构下不可能"。凡是前端能做的（图表、导出 CSV、URL 场景码），**一律不进后台**。

## 3. 架构设计

### 3.1 拓扑

浏览器同时连两处：静态页仍由 nginx 直出（`/elevator-twin/`，scp 发布不变），后台 API 经 nginx 反代到 `127.0.0.1:3600`（`/elevator-api/`）。后台内部三块：HTTP API（归档/场景/扫参提交）、Worker（无头仿真进程池）、WebSocket（遥测桥与扫参进度推送）。存储用单文件 SQLite，随服务进程本地读写。

### 3.2 技术选型与理由

| 选型 | 决定 | 理由 |
|---|---|---|
| 运行时 | Node 20 + Express | 与站内 cocreate/invite-api 同栈，运维一致 |
| 存储 | SQLite（better-sqlite3） | 单文件零运维；数据量级为万级运行记录，无需 PG；cocreate 的 Prisma+DB 属过度设计 |
| 进程 | PM2（name `elevator-api`） | 站内既有范式，开机自启与日志一致 |
| 仿真核心 | 抽为 ESM 模块，前后端同源共用 | **决定性前提**，见 3.3 |
| 实时 | ws（原生 WebSocket） | 对标 KONE Site Monitoring 的传输分工：WS 走高频状态，REST 走慢档配置 |
| 鉴权 | 无账号；写操作限流 + 体积上限 | 遵守既定非目标"不做账号体系" |

### 3.3 决定性前提：仿真核心同构抽取（ADR-01/03 兑现）

后台要跑扫参，就必须能在 Node 里跑仿真。E1 已经把这件事做成了**低成本**：`simTick()` 已是固定 0.02s 量子的纯推进函数、随机源已全部走注入式种子 PRNG、KPI 已全部以 `simClock` 计。剩下的工作只是把物理层（EU/ES/ElevatorAgent/genOD/KPI 聚合）从 index.html 剥离为 `sim-core.mjs`，前端 `import` 它、后端也 `import` 它。

**这一步同时关闭 E1 最后一项待办（PR-P0-1 的 Node runner）与本规划的 PR-BE-3**，是一石二鸟的关键动作，因此排在 E-BE-1。

**发布形态不变**：源码模块化后，前端发布仍产出**单个 HTML**（构建时把 sim-core 内联），scp 单文件流程与 C-1 约束不破。

### 3.4 数据模型（SQLite）

| 表 | 关键字段 | 说明 |
|---|---|---|
| runs | id, created_at, ver, seed, hour, floors, elevs, pop, demand, traffic, algo, sim_seconds, kpi_json, note | 一次运行的配置+KPI 摘要，是对比的基本单位 |
| run_pax | run_id, pid, from_f, to_f, spawn_s, wait_s, journey_s | 逐乘客账本，可选上传，单次上限 3000 行 |
| scenarios | id, created_at, name, cfg_json, hits | 命名场景，短链分享的落点 |
| sweeps | id, created_at, spec_json, status, progress, result_json | 扫参任务与排名结果 |

### 3.5 API 契约（草案，详见附录 A）

前缀统一 `/elevator-api/`。归档 `POST /runs`、`GET /runs`、`GET /runs/:id`；场景 `POST /scenarios`、`GET /scenarios/:id`；扫参 `POST /sweeps`、`GET /sweeps/:id`；遥测 `WS /telemetry`；健康 `GET /health`。

## 4. 核心设计原则（先于功能）

| 原则 | 内容 | 为什么 |
|---|---|---|
| **P-1 降级可用** | 后台不可达时，前端全部现有功能照常工作，只隐藏"保存/扫参"入口并提示 | 本产品最大的优点是"打开就用、零运维"；后台必须是增量，不能变成单点 |
| **P-2 无账号** | 不引入登录；归档用随机 runId 作能力令牌（知道 id 即可读） | 遵守既定非目标；降低隐私与运维面 |
| **P-3 确定性复算** | 归档必存 seed + 全配置 + 版本号；任何人凭记录可在前端一键复现该次运行 | 这是 E1 种子化工作的兑现点，也是"可信"的最终闭环 |
| **P-4 慢档 REST / 快档 WS** | 配置与结果走 REST，高频状态走 WebSocket | 对标 KONE 生产 API 的传输分工 |
| **P-5 有界与限流** | 单请求体 ≤1MB、单 IP 写 ≤30/分钟、账本 ≤3000 行、库 ≤500MB 滚动清理 | 公网无账号服务必须自我保护 |

## 5. 需求清单（PR-BE-x）

优先级 MoSCoW：M=Must、S=Should、C=Could。验收一律破坏性写法。

### 5.1 E-BE-1 基座（v0.12.0）

| 编号 | 优先级 | 需求 | 破坏性验收 |
|---|---|---|---|
| PR-BE-1 | M | 服务基座：Express+SQLite+PM2 上线于 3600，nginx 反代 `/elevator-api/`，`GET /health` 返回版本与库状态 | 杀掉进程后 PM2 自动拉起且 30s 内 health 恢复 200；重启服务器后自启 |
| PR-BE-2 | M | 运行归档：前端"保存本次运行"POST 配置+KPI；列表页可看历史与对比 | 断网状态下点保存：前端提示失败但仿真不中断（P-1）；重复提交同一 runId 不产生重复行 |
| PR-BE-3 | M | 仿真核心同构抽取 `sim-core.mjs`，Node 端 `node run-scenario.mjs --seed 42` 可跑并输出 KPI | 同种子下 Node 输出与浏览器 KPI **逐位相同**；前端发布产物仍为单 HTML 且体积增幅 <15% |
| PR-BE-9 | S | 生产日志汇：替换 localhost:8766，前端可选上报（默认关闭） | 关闭时零网络请求；开启时后台落盘且限流生效 |

### 5.2 E-BE-2 扫参（v0.13.0）

| 编号 | 优先级 | 需求 | 破坏性验收 |
|---|---|---|---|
| PR-BE-4 | S | 无头扫参：提交参数网格（梯数×速度×算法×需求），服务端并发跑，返回按 P95/AWT 排名 | 提交 24 组×10min 仿真，5 分钟内完成且进度可查；中途杀 worker，任务标记失败而非静默丢 |
| PR-BE-7 | S | 扫参进度 WebSocket 推送；断线重连续看 | 断网 30s 后重连，进度不回退、不重复计数 |
| PR-BE-8 | C | A/B 报告导出：扫参结果一键 CSV/图表 | 导出重算排名与页面一致 |

### 5.3 E-BE-3 遥测桥（v0.14.0）

| 编号 | 优先级 | 需求 | 破坏性验收 |
|---|---|---|---|
| PR-BE-6 | S | WebSocket 遥测桥：外部推 `{carId,floor,dir,doorPct}`，前端 ext 模式订阅渲染 | 10Hz 推流下前端延迟 <200ms；停推 10s 前端置灰（复用 PR-P2-6 心跳） |
| PR-BE-10 | C | 多端同看：同一房间号多浏览器看同一数据流 | 两标签页数据一致，晚加入者立即获得最后已知状态 |

### 5.4 E-BE-4 场景库（v0.15.0）

| 编号 | 优先级 | 需求 | 破坏性验收 |
|---|---|---|---|
| PR-BE-5 | S | 场景库与短链：命名保存配置，`/elevator-twin/?s=<id>` 打开即还原 | 换浏览器打开短链，楼层/梯数/算法/客流/种子全部还原，且复跑 KPI 与原记录一致（P-3） |

## 6. 阶段路线与版本映射

| 阶段 | 版本 | 主题 | 入口条件 | 出口标准 |
|---|---|---|---|---|
| E-BE-1 | v0.12.0 | 基座+归档+核心抽取 | 前端 E2 完成 | PR-BE-1/2/3 验收全过；杀后台前端功能不减（P-1 实测） |
| E-BE-2 | v0.13.0 | 无头扫参 | 依赖 PR-BE-3 | 24 组扫参 5 分钟出排名；worker 崩溃可见 |
| E-BE-3 | v0.14.0 | 遥测桥 | 依赖 PR-P2-6 心跳 | 10Hz 推流延迟达标；断流置灰 |
| E-BE-4 | v0.15.0 | 场景库短链 | 依赖 PR-BE-2 | 跨浏览器短链还原+复算一致 |

**顺序理由**：PR-BE-3（核心抽取）是扫参的硬前提，且顺带关闭 E1 遗留项，因此必须排在最前；遥测桥依赖前端心跳降级（PR-P2-6），故置于 E-BE-3。

## 7. 风险与取舍

| 风险 / 取舍 | 影响 | 缓解 |
|---|---|---|
| **引入后台即放弃"零运维"最大优点** | 多一个会挂的东西、多一份维护 | P-1 降级可用是硬约束：后台定位为"增量能力"，前端永不依赖它启动 |
| 单文件约束 C-1 与模块化冲突 | 发布流程可能变复杂 | 源码模块化、产物仍单 HTML（构建内联），scp 流程不变；构建脚本纳入发布清单 |
| `/api/` 前缀已被 invite-api 占用 | 直接用会 404 或串号 | 已定为 `/elevator-api/`，nginx 配置需人工核对不覆盖既有块 |
| 公网无账号写接口被滥用 | 刷库、占盘 | P-5 限流+体积上限+滚动清理；只存摘要，原始日志默认不收 |
| 扫参吃满 CPU 影响同机其他服务 | cocreate/invite-api 变慢 | worker 池上限 = 核数-1，nice 降优先级，任务排队而非并发无限 |
| SQLite 并发写瓶颈 | 高频写入阻塞 | WAL 模式；写操作是低频人工动作，非热路径 |
| nginx 改配置属高风险操作 | 改错全站 502 | 改前备份、`nginx -t` 校验、仅新增 location 不动既有；变更走 [[feedback_deploy_gateway]] 同等谨慎度 |

## 9. 非目标（显式不做）

| 不做 | 理由 |
|---|---|
| 账号体系、登录、权限 | 既定非目标；能力令牌足够，避免隐私与合规面 |
| 把仿真整体搬到服务端渲染 | 前端跑仿真是本产品的形态优势，后台只做前端做不到的事 |
| 多租户/组织空间 | 单人作品站，无此场景 |
| 替换现有静态发布链路 | scp 单文件仍是主发布路径，后台独立发布 |

## 附录 B 部署清单（实测命令模板）

1. 目录 `/home/ubuntu/elevator-api/`，`npm i express better-sqlite3 ws`
2. PM2 启动：`pm2 start server.js --name elevator-api` 后 `pm2 save`
3. nginx：备份 `battleai` 配置 → 新增 `location /elevator-api/ { proxy_pass http://127.0.0.1:3600/; }`（含 WS 需 `proxy_set_header Upgrade`）→ `sudo nginx -t` → `reload`
4. 验证：`curl https://opcstudio.cc/elevator-api/health` 返回 200 且 ver 与部署一致
5. 回滚：`pm2 stop elevator-api` + 恢复 nginx 备份 —— 前端应仍完全可用（P-1 回归项）
